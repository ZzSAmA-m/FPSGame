# 玩家伤害链路与延迟补偿方案（已实现）

方案日期为 2026-11-17，实施记录更新于 2026-11-18。碰撞箱审核通过后，已按本方案接入服务端权威伤害与延迟补偿。

玩家 Prefab 已绑定 `PlayerHitboxController` 与 `PlayerCombatPoseController`。身体仍使用审核通过的胶囊 Trigger，头部使用球体 Trigger，移动 CharacterController 保持独立。

## 1. 官方资料结论

CS2 的官方更新明确提到回溯目标 hitboxes，并修复过连续射击中的回溯时间偏差。另一次更新修复了丢包／抖动缓冲设置与延迟补偿的联动，并改善时钟同步。[Valve 2024 年 11 月官方更新正文](https://store.steampowered.com/news/posts/?appids=730&enddate=1731540103&feed=steam_community_announcements)

Valve 的 sub-tick 介绍说明服务器会获知开火等动作发生的时刻。本次找到的官方资料没有公开完整历史缓存结构、窗口长度和形状插值算法。本文的缓存与采样参数属于本项目设计建议。[Valve 官方 sub-tick 介绍](https://www.youtube.com/watch?v=GqhhFl5zgA0)

VALORANT 官方说明，开火输入附带与当时屏幕所显示模拟帧对应的时间戳。服务端使用历史位置和动画姿态判定命中，客户端收到权威结果后显示命中确认。[Riot 命中判定说明](https://playvalorant.com/en-us/news/dev/the-state-of-hit-registration/)

Riot 在 2020 年的服务器技术文章中披露过每四个服务器帧计算一次动画，并在历史动画之间插值的实现。本文提出的 60 Hz 球体与胶囊体采样属于本项目设计。[Riot 服务器动画与历史缓存说明](https://www.riotgames.com/en/news/valorants-128-tick-servers)

VALORANT 的 6.02 更新曾把最大回溯窗口从 200 ms 降到 140 ms。这是 2023 年公告中的参数，可用作公平性取舍的参考。[Riot 6.02 更新](https://playvalorant.com/en-us/news/game-updates/valorant-patch-notes-6-02/)

本项目采用服务端裁决、显示时间映射、历史几何插值和有限回溯窗口。首版输入与武器节奏按现有 60 Hz 推进，历史查询支持小数 Tick 插值。

## 2. 已布置的两个伤害触发器

修改资产为 `Assets/Prefabs/Player/Player.prefab`。本次资产布置使用现有 Collider 组件。

| 节点 | 父骨骼 | 形状 | 初始尺寸 | 层 | 标签 |
| --- | --- | --- | --- | --- | --- |
| `Hitbox_Head` | `head_0` | SphereCollider | 半径 0.18 m | Player（17） | Critical |
| `Hitbox_Body` | `pelvis` | CapsuleCollider，Y 轴 | 半径 0.40 m，高度 1.53 m | Player（17） | BodyShot |

两者都勾选 `Is Trigger`。身体胶囊使用 Collider 的局部 Y 轴，子节点旋转经过校准，使其在当前参考姿态中沿角色竖直方向摆放。骨盆的局部轴与角色竖直方向不同，因此子节点旋转包含骨骼轴向的补偿。

两个节点的位置如下。

```text
Player
└─ TPModelParent/Model/__meter_fbi/ctm_fbi/root_motion/pelvis
   ├─ Hitbox_Body
   └─ spine_0/spine_1/spine_2/spine_3/neck_0/head_0
      └─ Hitbox_Head
```

当前参考姿态下，以 Player 根节点为坐标基准，头部中心约为 `(0.0038, 1.6905, 0.0003)` m，身体中心约为 `(-0.0716, 0.7500, 0.0561)` m。日常调整使用各节点的局部 Transform 与 Collider 参数。

身体胶囊用于将躯干、手臂和双腿统一归为 Body，命中后统一使用 `BodyDamage`。一个粗略胶囊会包住肢体之间的部分空隙，无法贴合伸展四肢，动画伸展也可能使部分肢体超出范围。固定尺寸随骨盆移动与旋转，蹲姿时不会自动缩短，覆盖精度需要结合后续蹲姿规则复核。审核时应重点查看肩颈交界、双脚、手臂前伸和胶囊半径。

共享骨架会随 FP／TP 视角重父级。骨骼触发器随骨架一起移动，后续伤害裁决采样服务端的 TP 姿态。本地 FP 判定体从射击目标集合中按玩家身份排除。

预览文件位于 `Library/HitboxReview/front.png` 与 `Library/HitboxReview/side.png`。橙色表示头部球体，青色表示身体胶囊。

本阶段已核对以下内容。

- 玩家共有三个 Collider，其中两个为伤害 Trigger，一个为移动 CharacterController。
- 两个伤害 Trigger 均能通过 Collider 射线查询，并跟随父骨骼移动。
- 移动 CharacterController 的序列化数据与布置前一致。
- 玩家 Rigidbody 数量为零。射线查询 Trigger 可以直接使用 Collider 几何。
- 碰撞箱布置阶段没有改动 C#；审核通过后新增的运行时代码见下文。

## 3. 模块及数据归属

| 模块 | 责任 |
| --- | --- |
| `PlayerHitboxController` | 显式引用头部球体与身体胶囊，提供两个判定体的世界空间几何 |
| `ServerHitboxHistory` | 以服务器 Tick 保存固定容量历史，查询并插值指定时刻的两个判定体 |
| `ClientWorldTimeline` | 统一远端玩家的显示时间轴，发布最近一次呈现的服务器 Tick |
| `ServerShotTimeValidator` | 检查首次接收时间、视图年龄、顺序及快照区间，并限制最大回溯 |
| `ServerShotResolver` | 查询历史目标、检查遮挡、选择最近命中 |
| `ServerGameLogic` | 组织一拍全体玩家的推进、采样、射击和伤害提交 |

命中区域使用 `Head` 与 `Body` 两种类型。头部命中读取当前枪械定义中的 `HeadDamage`，所有非头部命中统一读取 `BodyDamage`。数值扣减与护甲分摊继续由 `PlayerStatsController.ApplyDamage()` 执行。

历史帧保存服务器 Tick、玩家身份、生命轮次、头部中心与半径，以及身体胶囊两端球心和半径。数据由 Collider 配置与最终骨骼 Transform 计算为世界空间几何。胶囊两端球心沿轴线按固定顺序记录，中心到各端球心的距离为 `max(高度 / 2 - 半径, 0)`。

生产 Prefab 同时记录玩家根节点、头部与骨盆的根相对位置和旋转，以及判定体相对骨骼的偏移。客户端快照按根位置线性插值、根 Yaw 最短路径插值、骨骼位置线性插值、骨骼旋转球面插值；服务端使用相同规则重建历史几何。半径线性插值。缺少骨骼姿态的隔离测试帧兼容世界空间几何插值。

快照附带 `combatContinuity`。远端收到重生或传送的新连续段后清空旧段样本，并拒绝迟到的旧段快照，避免显示跨段的中间位置。

两端球心重合或距离小于数值容差时，胶囊查询以两端球心的中点为中心，按相同半径的球体处理。出生、重生与传送建立新的历史连续段，查询只在同一连续段内插值。`ResetForSpawn()` 的出生序号用于隔离生命轮次，存活时执行出生重置也会隔离旧生命。权威 `PlayerSimulation.RestoreState()` 会打断历史连续性，普通预测恢复不影响服务端历史。直接修改 Transform 的传送代码还需显式调用 `Hitboxes.BreakContinuity()`。

## 4. 服务端每拍执行顺序

```text
收集本拍输入及射手存活资格
→ 全部玩家推进移动、切枪与武器输入，收集已确认开火
→ 全部玩家完成本拍动画和 TP 瞄准姿态求值
→ 记录本拍头部与身体判定体历史
→ 统一验证射击时间并查询历史命中
→ 批量提交伤害及死亡状态
→ 发布开火／命中结果和数值同步
```

`PlayerBrain.BeginServerStep()` 完成移动与切栏，`CompleteServerStep()` 推进武器；`StepServer()` 保留单玩家连续调用语义。输入上下文无论正常结束或异常退出都会清理。等待首批输入的现存玩家也参与姿态与历史采样。

`PlayerCombatPoseController` 接管服务器角色的动画时钟，暂停自动动画推进，按固定步长求值动作状态、Animator、动作结束与 TP 瞄准覆盖。同一 Unity 帧内补算多个 Tick 时，每拍独立求值；停止服务器生命周期时恢复原动画速度与裁剪设置。

`combat_pose_validate` 使用真实玩家 Prefab 验证手动时钟、同帧多拍、准备、射击、换弹、切枪，以及远端覆盖恢复。

实施时采用直接同步两条命中骨骼姿态的方式。公共快照包含 `PlayerCombatPose`；远端动画与 TP 瞄准运行后，在 `LateUpdate` 覆盖骨盆和头部的权威插值结果，下一帧先恢复覆盖，避免累计偏移。这样两个判定体使用统一的显示时间和动画姿态。其他骨骼与武器模型继续沿用既有动作事件表现；本地 FP 保持预测表现。

本拍推进开始前统一确认全部射手的存活资格，所有历史命中查询先于任何伤害提交，允许同一 Tick 内互换击杀。提交前再次检查目标当前存活状态与生命轮次，避免伤害回调内重生后承受旧生命的后续伤害。已经死亡的玩家从下一拍开始无法发射。

## 5. 射击时间映射

服务器快照与预测基准增加同一时钟域中的 `serverTime` 和 `serverTick` 锚点。客户端结合 Mirror 的时间同步建立公共显示时间轴，所有远端角色使用该时间轴进行插值。

公共时间轴发布 `LastPresentedServerTick` 及实际插值两端 `LastPresentedFromTick`、`LastPresentedToTick`。开火输入携带 `viewServerTick`、`viewFromTick`、`viewToTick`。服务端使用这两个真实快照端点重建几何，避免 60 Hz 历史与 30 Hz 快照、丢包后的插值端点不同。短点击保留按下时的三元组，同一渲染帧内补算输入沿用当时的显示基准。

`predictionEpoch + input.tick` 继续标识输入轮次和编号。玩家预测重同步时，输入轮次更新，公共显示时间轴保持在服务器时间域中。

`viewServerTick` 已经包含远端显示缓冲的影响。服务端直接用经过校验的视图时间查询历史，RTT 与输入排队时间用于合理性校验，避免重复扣除插值延迟。

服务端记录输入首次到达的时刻，冗余输入不改写首次接收时间。Mirror 的 `NetworkTime.time` 是客户端的快照显示时间轴；移除其自带缓冲后仍保留实际下行耗时。本项目再叠加 30 ms 显示缓冲，因此首次接收时的预期视图年龄按 `RTT + 30 ms` 校验，容差为 50 ms。服务器排队时间由首次接收至执行的 Tick 差体现，不重复从请求时间扣除。时间必须为有限值，按输入顺序检查时间倒退，并对异常未来值、年龄及快照区间给出明确拒绝原因。

回溯窗口以服务端执行该发命中查询时的模拟 Tick 为上界，200 ms 表示该时刻至实际历史查询时刻的总跨度，涵盖视图延后、网络传输和服务器等待的影响。校验容差用于处理合理估计误差，窗口上限独立生效。

合法时间超过最大回溯窗口时，查询夹取到窗口下界，改用该时刻附近的服务器历史采样；超窗视图无法保证与原始客户端画面完全一致。异常时间导致该发伤害判定失败，并记录原因。已经确认的权威开火和扣弹保留其原有结果。

## 6. 历史命中与遮挡查询

射线起点和方向使用服务端认可的玩家状态与视角构造。客户端提交开火意图与视图时间，目标和命中部位由服务器查询产生。

首先检查视线原点到前移射击原点之间的短线段，再检查最大射程内的地图阻挡，避免现有 0.3 m 射线前移距离越过近处墙体。地图查询过滤玩家层级下的 Collider，并使用 `QueryTriggerInteraction.Ignore`。

玩家查询从历史帧取得头部球体和身体胶囊，执行射线与 Sphere／Capsule 的数学相交测试。胶囊两端球心重合或距离小于数值容差时执行球体相交测试，避免退化轴线导致除零。射手自身按玩家 ID 排除。查询在历史几何数据上执行，当前场景物体的位置用于本拍运行。

对所有目标与区域比较首次交点距离，并与地图阻挡距离比较，选择最近有效命中。每发子弹提交一次目标伤害。头部与身体交点在 1 mm 容差内相等时按 Head 归类，其余情况按交点距离判定。

当前方案按静态地图遮挡实现。将来加入动态门或可移动掩体时，需要把这些遮挡物纳入相应的历史查询。

历史不足、目标尚未出生、目标已离开或跨越生命轮次时，输出对应的查询失败原因。伤害最终提交到目标当前生命状态，死亡通知按现有数值模块规则触发。

服务器提交伤害后，向所有就绪客户端可靠广播该次命中，提供射击 ID、射手 ID、目标 ID、Head／Body、命中位置和是否致死。受击者通过所属客户端数值消息接收精确生命和护甲。公开存活状态通过独立的可靠消息同步。

## 7. 首版参数

| 参数 | 当前默认值 | 用途 |

| 模拟和判定体采样频率 | 60 Hz | 与现有固定步长对齐 |

## 8. 验收条件

- 头部和身体查询分别选用对应伤害，同一发子弹只提交一次伤害。
- 静止、横移、跳跃、俯仰、换弹与已有姿态动作的判定体采样符合各自服务器 Tick。
- 服务器单帧补算多个 Tick 时，历史姿态随各拍正确推进。
- 使用 0、50、100、200 ms RTT 及丢包／抖动场景，对照客户端呈现时间与服务端查询姿态，分别记录总回溯跨度与是否触及窗口上限。
- 未来时间、过旧时间、重复输入、时间倒退及预测重同步按上述规则处理。
- 地图墙体及视线起点前方 0.3 m 内的阻挡能够截断射击。
- 多目标、头身边界与遮挡距离均按最近交点选择结果。
- 胶囊端点和半径插值保持对应顺序，退化为球体时仍能正确求交。
- 同 Tick 互换、目标死亡、重生、传送、断线和重新加入均保持历史连续段与当前数值一致。
- 每次提交伤害的命中向所有就绪客户端广播一次。精确生命与护甲仅发送给受击玩家本人，客户端收到命中消息时只分发通知。
- Editor 调试记录包含射击 ID、输入 Tick、执行 Tick、请求／实际查询 Tick、命中区域、距离和失败原因，并可显示实际查询的历史形状。

`ServerManager.ShotResolved` 提供射击记录，包含输入 Tick、执行 Tick、首次接收 Tick、RTT、请求与实际查询 Tick、拒绝原因、命中区域及实际伤害。Editor 中选中 ServerManager 可以显示最近一批射击所用的历史形状。`ClientManager.HitReceived` 提供公共命中结果订阅入口，`ClientManager.HitConfirmed` 仅在本地玩家是射手时通知。客户端按射击 ID 去重。

Editor 隔离验证命令为 `combat_geometry_validate`、`combat_timeline_validate`、`combat_pose_validate`、`combat_server_validate`。`combat_probe` 仅编入 Editor，用于真实 KCP 多进程测试和普通输入注入，不进入游戏构建。

最大回溯按执行 Tick 计算，包含显示延后、网络传输与服务器等待，因此附加 100 ms RTT 的样本也可能触及上限。本轮未夹取的样本中，服务端重建头部中心与客户端实际显示位置的最大差值约为 0.001228 mm，身体端点差值约为 0.00003 mm；这只表示这些样本的插值一致性，不代表所有动画或网络条件下的通用误差上限。记录位于 `Library/CombatValidation/11-latency-summary.json` 及同编号的服务端／视图明细。

## 10. 协议 9 的命中广播与死亡停控（2026-11-18）

本机 `PlayerController` 将权威生命状态通过 `EventCenter` 发布给 `PlayerInputDriver`。输入层的 `DisableInput()` 和 `EnableInput()` 会清除积压输入，死亡期间仍按拍提交无操作帧。服务端按拍开始的存活资格屏蔽操作，保留同拍互换击杀。客户端在死亡期间回放旧输入时也屏蔽操作，物理继续推进。

Unity Pipeline 编译通过，14 组回归共通过 208 项检查。独立服务端与射手、受击者、观察者三个 KCP 客户端通过以下在线验证。

- 移动目标的身体命中使用约 117 ms 的历史几何，护甲与生命各扣 25。三个客户端收到相同的公共命中，射手收到本机确认，受击者收到精确数值。
- 视线原点前 0.15 m 的墙体阻挡射击，没有产生公共命中或伤害。
- 无甲目标的致死头部命中后三端同步 `Dead`，精确生命归零只发给受击者。死亡期间输入确认继续推进，积压及新输入没有产生操作，观察者仍能操作。服务端恢复 `Alive` 后，受击者可重新操作。

验证记录位于 `Library/CombatValidation/15-protocol9-regression.json` 和同目录 `16a` 至 `16e` 的在线测试文件。子弹轨迹、血迹、死亡动画和自动重生留待后续玩法接入。
