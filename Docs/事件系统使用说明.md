# 整数 ID 事件系统使用说明

事件中心位于 `Core.Event.EventCenter`。事件先按整数 ID、名称和完整参数签名注册，再添加监听并同步发布。发布支持零到三个参数，使用强类型 `Action`，不通过 `object[]` 传递参数。

## 1. 文件与职责

| 文件或类型 | 职责 |
| --- | --- |
| `Assets/Scripts/Core/Event/EventCenter.cs` | 对外注册、订阅、退订、发布、日志配置与重置入口 |
| `EventRegistry`、`EventDescriptor` | 保存 ID 对应的定义、名称和委托签名 |
| `EventChannel` 及泛型版本 | 保存对应签名的监听列表，执行分发和清理 |
| `ListenerEntry` | 保存原始委托、有效标记和订阅时缓存的诊断信息 |
| `EventLogger`、`EventLogOptions` | 控制发布日志、详细调用记录和日志重入 |
| `Assets/Scripts/GamePlay/Events/CameraEventIds.cs` | 定义相机玩法事件编号 |
| `Assets/Scripts/GamePlay/Events/GameEventBootstrap.cs` | 在运行启动时重置并注册玩法事件 |
| `Assets/Editor/Validation/EventSystemValidation.cs` | 编辑模式行为与发布分配检查 |

核心层不知道相机、玩家或武器类型。玩法层使用自己的 ID 字段和注册入口，把业务签名交给事件中心。

## 2. 初始化与生命周期

所有事件 API 都应在 Unity 主线程调用。事件中心第一次调用 `Reset()` 时记录当前线程，并不能自行判断它是不是 Unity 主线程，因此必须由启动入口保证首次调用在 Unity 主线程。初始化后，其他线程的调用会拒绝执行并记录诊断；未初始化时除 `Reset()` 外的 API 也会拒绝执行。

项目启动入口为 `GamePlay.Events.GameEventBootstrap`。它在 `RuntimeInitializeLoadType.SubsystemRegistration` 阶段执行：

```text
进入新的运行会话
  → EventCenter.Reset()
  → GameEventBootstrap.RegisterAll()
  → 场景对象 Awake / OnEnable
  → 对象添加监听
```

该入口也覆盖关闭 Domain Reload 后再次进入 Play 的情况。普通场景切换不调用 `Reset()`；否则仍然存活的场景服务会失去监听，而这些对象不一定再次触发 `OnEnable`。

这个初始化入口针对每次进入 Play，不保证 Play 中脚本热重编译或域重载后自动恢复注册与监听。遇到这种情况，退出后重新进入 Play。

`Reset()` 会清除所有事件定义、监听和每事件日志配置，不是“刷新一下注册”。分发期间调用会被拒绝，不能用它终止当前遍历。完整重启事件系统时，调用方需要重新注册定义，再让仍然存在的服务明确重新订阅。

## 3. 用字符串哈希声明事件 ID

ID 统一声明为 `public static readonly int EventName = "ClassName.EventName".GetHashCode();`。哈希输入使用声明类名和字段名组成的字面量，在每次类型初始化时计算一次，之后订阅和发布只读取该 `int` 字段，不重复计算哈希。不要在 ID 类型的静态初始化中注册事件，仍由启动入口统一注册。

现有相机事件：

| ID 字段 | 计算表达式 | 参数 | 含义 |
| --- | --- | --- | --- |
| `CameraEventIds.Attach` | `"CameraEventIds.Attach".GetHashCode()` | `Transform` | 场景相机挂到指定玩家挂点 |
| `CameraEventIds.Detach` | `"CameraEventIds.Detach".GetHashCode()` | 无 | 场景相机回到原父节点 |

新增业务模块可以定义自己的 ID 声明类。例如下列是说明用的新模块，不需要修改事件中心：

```csharp
namespace GamePlay.Events
{
    /// <summary>集中声明战斗模块使用的事件编号。</summary>
    public static class CombatEventIds
    {
        /// <summary>战斗已开始，不携带参数。</summary>
        public static readonly int Started = "CombatEventIds.Started".GetHashCode();

        /// <summary>分数变化，参数为当前分数。</summary>
        public static readonly int ScoreChanged = "CombatEventIds.ScoreChanged".GetHashCode();

        /// <summary>受到伤害，参数为玩家编号和伤害量。</summary>
        public static readonly int Damaged = "CombatEventIds.Damaged".GetHashCode();

        /// <summary>命中目标，参数为攻击者、伤害和命中点。</summary>
        public static readonly int Hit = "CombatEventIds.Hit".GetHashCode();
    }
}
```

哈希值不保证跨进程、平台或运行时版本稳定，只用于当前进程的本地事件，不作为网络协议编号或存档数据。不同字符串也可能得到相同哈希；注册时保留含命名空间的完整名称，现有冲突检查会拒绝同 ID 下名称或签名不同的注册，不覆盖旧定义。不同命名空间也应避免同名事件声明类：相同类名和字段名会生成完全相同的哈希输入，完整注册名称虽能检测冲突，却不能让两个事件同时使用该 ID。

把注册调用放入对应的业务初始化入口，并由 `GameEventBootstrap.RegisterAll()` 统一调用该入口。哈希输入是简短的 `ClassName.EventName`，注册名称继续使用含命名空间的全限定名，便于诊断和冲突检查。下面用一个独立方法展示四种参数数量：

```csharp
using Core.Event;
using UnityEngine;

namespace GamePlay.Events
{
    /// <summary>注册战斗模块的全部事件定义。</summary>
    public static class CombatEventRegistration
    {
        /// <summary>逐项注册并返回是否全部成功。</summary>
        public static bool RegisterAll()
        {
            bool started = EventCenter.Register(
                CombatEventIds.Started, "GamePlay.Events.CombatEventIds.Started");
            bool score = EventCenter.Register<int>(
                CombatEventIds.ScoreChanged, "GamePlay.Events.CombatEventIds.ScoreChanged");
            bool damaged = EventCenter.Register<int, float>(
                CombatEventIds.Damaged, "GamePlay.Events.CombatEventIds.Damaged");
            bool hit = EventCenter.Register<int, float, Vector3>(
                CombatEventIds.Hit, "GamePlay.Events.CombatEventIds.Hit");
            return started && score && damaged && hit;
        }
    }
}
```

同一个 ID 使用完全相同的名称和参数签名再次注册，返回 `true`，保留已有监听和日志配置。名称、参数数量、参数类型或参数顺序不同则返回 `false`，记录冲突，不覆盖原事件。

不要把 ID 当成唯一的运行时类型保证。即使 ID 相同，`Register<int, float>` 与 `Publish<float, int>` 仍然是签名错误。

## 4. 添加和移除监听

`AddListener` 支持可选的 `owner`。它仅用于日志归属，不参与重复判断，也不表示弱引用或自动退订。

```csharp
using System;
using Core.Event;
using GamePlay.Events;
using UnityEngine;

namespace GamePlay.UI
{
    /// <summary>示范按组件生命周期监听伤害事件。</summary>
    public sealed class DamageEventExample : MonoBehaviour
    {
        /// <summary>缓存对应的强类型监听委托。</summary>
        private Action<int, float> _damageListener;

        /// <summary>本组件累计接收的伤害量。</summary>
        private float _receivedDamage;

        /// <summary>在启用前建立稳定的监听委托。</summary>
        private void Awake()
        {
            _damageListener = OnDamaged;
        }

        /// <summary>启用时订阅已经注册的事件。</summary>
        private void OnEnable()
        {
            EventCenter.AddListener<int, float>(
                CombatEventIds.Damaged, _damageListener, owner: this);
        }

        /// <summary>停用时移除同一组监听。</summary>
        private void OnDisable()
        {
            EventCenter.RemoveListener<int, float>(
                CombatEventIds.Damaged, _damageListener);
        }

        /// <summary>同步处理已经收到的伤害参数。</summary>
        private void OnDamaged(int playerId, float damage)
        {
            _receivedDamage += damage;
        }
    }
}
```

使用具名方法时，同一个目标实例上的同一个方法可被正常判重和移除；不同实例上的同名方法是两个独立监听。缓存委托可以减少反复启用时的委托创建。

重复键为“事件 ID + 原始委托”。同一原委托换一个 `owner` 再添加仍返回 `false` 并警告，不会更改原监听的 owner。空委托、多播委托都拒绝；请逐个调用 `AddListener`，不要先用 `callbackA + callbackB` 组合后再提交。

如果使用 lambda，需要保存添加时的委托。重新写一个看起来一样的 lambda 不能可靠地移除旧监听。不要让静态事件长期持有已不再使用的对象。

### Unity 对象销毁的边界

- 回调直接绑定的 `callback.Target` 是 `UnityEngine.Object` 且已销毁时，发布会跳过并清理该监听。
- 显式传入的 `owner` 只是诊断数据。owner 销毁不会自动移除一个绑定到其他对象或闭包的回调。
- lambda 捕获 MonoBehaviour 时，直接委托目标可能是闭包对象，不能把它当成直接绑定 Unity 对象的情况。
- 无论是否有销毁保护，都应通过 `OnDisable` 或明确的释放入口退订；销毁检查不是生命周期管理的替代品。

## 5. 发布与类型推断

```csharp
// 零参数。
EventCenter.Publish(CombatEventIds.Started);

// 一参数，T1 推断为 int。
EventCenter.Publish(CombatEventIds.ScoreChanged, 120);

// 二参数，float 使用 f 后缀，避免被推断为 double。
EventCenter.Publish(CombatEventIds.Damaged, 7, 12.5f);

// 三参数，按注册的顺序传递值类型。
EventCenter.Publish(CombatEventIds.Hit, 7, 12.5f, new Vector3(1f, 2f, 3f));

// null 无法可靠推断类型时，明确写出已注册的签名。
EventCenter.Publish<Transform>(CameraEventIds.Attach, null);
```

最后一行只用于说明泛型写法：现有相机监听要求有效挂点，真实业务不应给它发布空值。

`Publish` 在当前主线程同步执行，返回时当前轮监听已处理完毕。它不是异步任务队列，也不负责跨线程调度。后台线程得到的结果应先通过现有主线程调度入口送回 Unity 主线程，再发布。

如果事件注册为 `object`，发布一个字符串时需要明确 `Publish<object>(id, text)`；直接传字符串会推断为 `string`，与注册签名不同。`int`、`float`、`Vector3` 等值类型通过对应泛型通道直接传递，正常发布不会为了参数传输而装箱。

对裸方法组添加或移除泛型监听时，建议明确写 `AddListener<Transform>`、`RemoveListener<Transform>`。缓存为 `Action<Transform>` 的变量通常可以由编译器推断。合法的 `Action<object>` → `Action<string>` 逆变也支持，但事件的注册/发布签名仍应明确为 `string`，并保留原委托身份。

## 6. 回调期间修改监听的规则

| 操作 | 当次发布 | 下一次发布 |
| --- | --- | --- |
| 移除尚未执行的监听 | 该监听被跳过 | 不再调用 |
| 移除正在执行的自身 | 当前方法继续返回 | 不再调用 |
| 新增监听 | 不加入当次固定遍历范围 | 按新增位置调用 |
| 自退订后立即重新订阅 | 不在当次再次执行 | 新订阅排到后面 |
| 当前事件再次发布自身 | 拒绝并诊断 | 外层仍继续执行 |
| 发布另一个事件 | 立即同步嵌套执行 | 返回后继续外层 |
| 一个监听抛出异常 | 记录错误，继续后续监听 | 事件仍可再次发布 |
| 分发中 Reset | 拒绝重置 | 分发结束后可在系统重启流程中重置 |

内部以发布开始时的监听数量为上限，删除先标记失效，结束时在 `finally` 中压实列表。既避免迭代时直接移除造成跳项，也不需要每次发布复制列表。

如果 A 发布 B，B 又发布尚未结束的 A，第二次 A 仍属于同事件递归，会被拒绝。允许不同事件嵌套不代表允许循环事件链。

异常隔离不提供业务回滚。一个监听在抛错前已经修改的数据不会自动恢复。需要事务语义的业务应在自己的逻辑层处理。

## 7. 日志与性能边界

事件日志使用 `LogChannel.Event`，沿用项目 ZLog Console 过滤面板。

| 日志 | 默认频率 | 内容 |
| --- | --- | --- |
| 注册、幂等注册、添加、移除、重复或签名错误 | `Low` | 定义、原委托和监听数量等诊断 |
| 发布汇总 | `Medium` | 发布编号、事件定义、开始数量和结束统计 |
| 逐监听明细 | `Medium` | 实际成功、异常或被跳过的方法 |
| 监听异常 | `Low` 错误 | 事件、方法及异常信息 |

默认开启发布汇总与逐监听明细。每个事件可以单独调整：

```csharp
using Core.Event;
using Core.ZLog;

// 高频业务使用 High；关闭逐方法明细但仍保留发布开始/结束汇总。
EventCenter.ConfigurePublishLog(CombatEventIds.ScoreChanged, LogFrequency.High, false);

// 需要逐方法诊断时恢复详细输出。
EventCenter.ConfigurePublishLog(CombatEventIds.ScoreChanged, LogFrequency.Extreme, true);

// 在拼接自定义诊断之前判断过滤结果。
if (Core.ZLog.ZLog.ShouldLog(LogChannel.Event, LogFrequency.High))
{
    Core.ZLog.ZLog.Log("这里再生成较贵的诊断文本", LogChannel.Event, LogFrequency.High);
}
```

`ConfigurePublishLog` 的频率只允许 `Medium`、`High`、`Extreme`。无效频率或未注册 ID 返回 `false`，不修改已有配置。它不会改变业务是否分发；关闭日志也不会停止监听执行。

### “零 GC”具体指什么

注册、添加、移除会分配事件对象、监听条目、诊断字符串或委托；单播校验也会调用 `GetInvocationList()`，因此不承诺订阅与退订零分配。

正常发布的承诺范围是：**完成泛型与路径预热后，匹配的已注册事件同步发布，监听自身不分配，并且发布日志被过滤时，事件中心的热路径不产生托管分配。** 可通过以下任一种方式过滤对应发布日志：

- `ZLog.Enable = false`。
- `ZLog.SetChannelVisible(LogChannel.Event, false)`。
- 关闭该事件配置使用的频率，例如默认事件关闭 `LogFrequency.Medium`。

**只把 `detailed` 设为 `false` 不等于零 GC。** 发布开始和结束汇总仍会生成字符串并写入 Console。Console 输出、异常处理、错误签名、监听内部的字符串拼接、新建集合或委托都不在正常零分配热路径范围内。

发布开始时会捕获该轮的频率、明细配置和日志可见状态；回调中修改配置主要面向后续发布。实际写入前也会再次遵守当前 ZLog 过滤，不会为了已经过滤的日志提前构造文本。

事件日志自身有线程局部的写入保护。如果 `Application.logMessageReceived` 或自定义 `ILogHandler` 再次发布事件，嵌套过程中的事件日志会被抑制，避免“错误日志又触发错误日志”的无限循环。业务分发仍遵守前述规则：同事件递归拒绝，不同事件可同步嵌套。不要依赖日志回调来驱动核心玩法。

ZLog 的 Frequency 是显隐标签，不是按帧抽样器。玩家构建默认不会读取编辑器过滤偏好，需要时由运行时明确配置日志开关。

## 8. 常用 API 返回值

| 调用 | 结果 |
| --- | --- |
| `Register` | 新注册或同定义幂等注册为 `true`；冲突或非法请求为 `false` |
| `AddListener` | 实际添加成功为 `true`；重复、空回调、多播或类型错误为 `false` |
| `RemoveListener` | 实际移除一个有效原委托为 `true`；未找到或非法请求为 `false` |
| `Publish` | 无返回值；错误请求记录日志并拒绝，监听异常逐项隔离 |
| `ConfigurePublishLog` | ID 与频率有效时为 `true` |
| `IsRegistered` | 返回该 ID 是否已注册，不创建事件 |
| `GetListenerCount` | 返回有效监听数量；未注册记录错误并返回 `-1` |
| `Reset` | 主线程且不在分发中时清空并返回 `true` |

所有错误日志仍受 ZLog 总开关、Event 分类及对应频率过滤。关闭诊断后，请通过返回值判断注册、订阅等操作是否成功。

## 9. 从旧接口迁移

旧的 `GameEvent` 对象和嵌套 `EventCenter.GamePlayEvent` 已由整数 ID API 替换：

| 旧写法 | 新写法 |
| --- | --- |
| `EventCenter.GamePlayEvent.CameraAttachEvent.OnEventRaised += AttachCameraToModel` | `EventCenter.AddListener<Transform>(CameraEventIds.Attach, AttachCameraToModel, this)` |
| `...CameraAttachEvent.OnEventRaised -= AttachCameraToModel` | `EventCenter.RemoveListener<Transform>(CameraEventIds.Attach, AttachCameraToModel)` |
| `...CameraAttachEvent.RaiseEvent(point)` | `EventCenter.Publish<Transform>(CameraEventIds.Attach, point)` |
| `...CameraDetachEvent.RaiseEvent()` | `EventCenter.Publish(CameraEventIds.Detach)` |
| `EventCenter.showDetail`、`showEventInvokeMsg` | 每事件 `ConfigurePublishLog` 与 ZLog Event/频率过滤 |

不要把旧事件对象和新 ID 系统同时用于同一业务，否则会出现一部分监听只收到旧发布的情况。现有相机注册已集中到 GameEventBootstrap，相机服务只负责添加/移除监听，玩家相机逻辑只负责发布。
